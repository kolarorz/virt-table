对宿主表格的要求、三个层的遮挡规则、时间轴范围的判定，以及纯逻辑层。

## 对宿主表格的要求

| 要求 | 为什么 |
| --- | --- |
| `fixedSize: true`（固定行高） | **建议而非必须**。条的纵向几何取自 `getRenderedRowRects()`（真实 DOM 矩形），不定高也精确；建议固定只是因为甘特的行本来就该等高。二期做依赖箭头时会变成硬要求 —— 箭头的另一端常在渲染窗口外，那时只能按行位置账本外推 |
| 业务列的 `fixed` **交给插件归一** | 规则是「开头那串功能列（勾选 / 序号 / 拖拽手柄 / 展开）+ 第一个数据列」冻结、其余解冻（`freezeFirstColumn: false` 可全解冻）。**`type: 'tree'` 算数据列**（它只多了缩进与折叠箭头，值仍是字段值 —— 与核心 `isDataColumn` 同一条规则），所以 WBS 里冻结停在树形任务名上，负责人那些列跟着面板横滚。**全冻不行** —— 冻结列不参与滚动，那等于把面板自己的横滚废掉；**全解冻也不行** —— 面板横滚时任务名跟着滚走，那一行是谁就看不出来了 |
| 表头高度由插件抬高 | 时间轴表头要塞两行（年月 + 日期），核心默认的一行高度（约 42px）太挤。插件按实测**反解** `--vt-header-padding-y`（表头专用，不碰表体 padding，所以不影响行高不变量），左表与时间轴因此一起长 —— pane 的表头高度是照左表 thead 实测的。`headerHeight` 可调，给 `0` 不干预 |
| 行拖拽排序两个入口并存 | 手柄列（`type: 'drag'`）+ 核心 `vtRowDrag` 走 `moveRowTo()`，**树形 / 分组下也能拖**；甘特条上的纵向拖走 `editable.reorder`，只在扁平形态下可用。两者不打架：甘特的手势排除了 `.vt-drag-handle`，而 `vtRowDrag` 只从手柄发起 |
| 时间轴那侧**没有列** | 它是插件自己的 pane，所以 `merges` / 列显隐 / 列宽 / 导出都只作用于业务列 |

想让表格与甘特是**同一份数据**，把那几列绑到同一批字段上就行 —— 核心的列组件都有
`onChange`，在里面调一次 `refreshGantt()`：

```ts
columns: [
  { key: 'name', title: '任务', width: 240, type: 'tree' },
  VtSelect({ key: 'status', title: '状态', width: 104,
             options: STATUS, display: 'tag', onChange: () => table.refreshGantt() }),
  VtDatePicker({ key: 'start', title: '开始', width: 118,
                 clearable: true, onChange: () => table.refreshGantt() }),
  VtDatePicker({ key: 'end', title: '结束', width: 118,
                 clearable: true, onChange: () => table.refreshGantt() }),
  // editable: true 之后编辑态是个滑块（核心 0.0.2 起）
  VtProgress({ key: 'progress', title: '进度', width: 132,
               editable: true, onChange: () => table.refreshGantt() }),
]
```

`clearable: true` 给日期列一个 `×`（在编辑态里），清空后那一行回到未排期、条消失，
可以用 `editable.create` 重新点出来。

那几行 `onChange: () => table.refreshGantt()` 是**核心缺 `onCellEdit` 的临时补丁**
（见仓库 AGENTS.md 的已知缺口）：插件收不到「某格被改了」的通知，而汇总条有一张
按行 key 的记忆表要作废。核心补上那个钩子之后就能删。

### 为什么是两个 pane（而不是一张表）

一期整张甘特是**一张** `<table>`：一个时间桶 = 一个 `VirtTableColumn`，于是横向虚拟化、
年/月两级表头、网格线全由核心免费提供。但那样左右**共用同一个滚动容器** ——
`.vt-client` 是唯一的 `overflow-x: auto`，而业务列是 `position: sticky` 的 `td`，
sticky 的列根本不参与滚动。业务列一旦总宽超过容器，最右边几列会被钉到视口之外，横滚也够不到。

「左表格与右甘特各自横滚」要求**两个滚动视口**，这与「全在同一张表里」互斥。现在的结构：

```
.vtp-gantt-split                 flex 容器（插件插进来，包住使用方的 root）
├─ .vt-root                      使用方的表格 = 左 pane（只装业务列）
└─ .vtp-gantt-pane               右 pane，自己的 overflow-x
     └─ .vtp-gantt-pane__content 宽 = 桶数 × 桶宽
          ├─ .vtp-gantt-pane__head   时间轴表头（两行，sticky top）
          └─ bg / static / bars      底纹网格 / 标记 / 条
```

**行永远只由左表拥有**（单行模型）：pane 里一行 DOM 都没有，条的纵坐标取
`getRenderedRowRects()` 再加一个实测差值换算到 pane 的内容坐标系。

另一条路是「两个 `VirtTable` 实例」—— 那要把行模型复制两份、纵向靠 JS 互同步，正是
dhtmlx / frappe 那类实现卡顿与错行的来源；而且核心的分组行天生 42~43px，镜像成普通行只有
40px，每个分组行漂 3px 并逐行累积。单行模型下**行对齐是构造上就对的**，不依赖任何同步。

代价（都是真的，写在这里而不是藏起来）：

- 时间轴那侧**没有单元格** → 框选、键盘导航、单元格编辑、导出都只覆盖业务列；
- 两级表头的「跨窗口裁剪」得自己写（见下一节）；
- pane 自己不纵滚，在它上面滚滚轮由 JS 桥接给左表（`scrollByY`）—— 位移路径上**唯一**一处
  为双 pane 付出的 JS 成本，横滚仍然零 JS；
- 滚动条要自己画（见下）。

#### 滚动条：三条，都是自绘的

甘特上一共三条滚动条，一条都不是原生的：

| 条 | 代表什么 | 谁画的 |
| --- | --- | --- |
| 左下横条 | 任务面板的横向位置 | 核心（`.vt-root` 里那条） |
| 右下横条 | 时间轴的横向位置 | 插件（贴 pane 底边，起点让开左表那一段） |
| 最右竖条 | **行**的纵向位置 | 插件（贴整幅甘特的右缘，从时间轴表头下缘起） |

**时间轴那侧为什么不能用原生的**：pane 确实是真 scrollport，但 macOS 的浮层滚动条只在滚动
那一瞬间出现，「hover 显形」原生做不到；给 `::-webkit-scrollbar` 上尺寸又会在 Windows / Linux
上变成占位的经典滚动条、吃掉 pane 底部十几像素 —— 而行是左表给的，pane 矮一截的结果是最后
一行的条被裁掉一半。所以 pane 的原生滚动条整个关掉（`scrollbar-width: none`），横条自绘。

**竖条为什么归插件、而且只有一条**：纵向只有一份真相（行永远只由左表拥有），所以竖条也只该
有一条。核心画的那条落在 `.vt-root` 右缘 —— 双 pane 下那是两个 pane 的**分界处**，也就是整幅
画面的中间，而任务面板一收起（root 宽度 0）它连位置都没有了。于是那条被藏掉，插件在最外缘
另画一条：位置与收起状态无关，也与各家甘特（Jira / TeamGantt）一致。它没法用原生的 ——
pane 里一行 DOM 都没有，`scrollHeight` 恒等于 `clientHeight`，浏览器压根不认为它能纵滚。

实现是核心的 `@virt-table/vanilla/scrollbar`（与左表那条**同一个类**），所以拖拽手感、轨道
点击跳转、淡出时机、暗色主题在整个组件里是同一份实现。两个细节：

- 三条**一起**在「指针悬在甘特上」时显形（含左表那条 —— 核心原本的规则是「指针在表格上」，
  手停在时间轴那侧时它不亮，插件把范围放宽到整幅 split）。淡出时机与滑块下限跟着表格的
  `scrollbarAutoHide` / `scrollbarMinThumbSize` 走：一个组件不该有两套手感。
- 竖条要知道**内容总高**，而 pane 算不出来（它没有行）。插件在每帧同步里按末行矩形反推
  （`getRowRect(n-1).top + getOffset() + height`），并且**只在行的构成变了时重算**
  （`onDataChanged` / `onColumnsChanged`）—— 滚动不改变内容总高，每帧多量一趟白付钱。
  拖滑块落位走 `scrollByY`（用户语义、会触发触底续拉），不走程序化的 `scrollToOffset`。
- 三条的**下沿是一条线**，而这条线不是「容器底边」：核心那条横条是 `.vt-root` 的绝对定位
  子节点，`bottom: 0` 落在**边框内沿**上，而 pane 刻意不带边框 —— 直接写 `bottom: 0` 的话
  两条横条的滑块差 1px 高。插件量出左表下边框的厚度当基线（`--vtp-gantt-frame-b`，
  `border: false` 时它就是 `0px`）。

#### 面板宽度的一条硬不变量：时间轴至少 120px

面板宽度是 `.vt-root` 上的 `flex: 0 0 <w>px`，所以 `w` 一旦大于容器宽，时间轴就是 **0 宽**。
那不只是「看不见」——**分界**（`.vtp-gantt-resizer`）与**收起任务表**那颗按钮都长在时间轴那一侧，
0 宽之后两个都在容器之外：拖不到、点不着，甘特再也回不来。所以宽度有三个入口
（`panelWidth` 初始值、拖分界、`setPanelWidth()` / 收起展开），三个都过同一个钳子
`min(要的宽度, 容器宽 − 120)`。

还有一条 `ResizeObserver` 盯着容器：窗口缩小时面板跟着收，宽回来再还回**原本要的**那个宽度
（内部分 `desired` / `width` 两个值就是为了这个 —— 只留一个的话，缩一次窗口就把用户拖出来的
宽度永久吃掉了）。容器宽度量不到（无布局环境 / SSR）时不钳：那时候钳出来是 0，等于把面板整个收掉。

### 时间轴表头是插件自己画的

两行：上层年月/年（相邻同值的桶合成一格），下层每桶一格。三件事值得记：

1. **高度取左表 thead 的实测高度**，两行按 44% / 56% 分。不去拼「一行多高 × 几行」——
   使用方可能自己就有多级表头，实测求高永远对。
2. **桶格全量渲染**，不做横向虚拟化：桶宽恒等，`maxBuckets` 个 div 一次建好，
   横滚由合成器平移。做窗口化就得在滚动时重建 DOM，反而把「零 JS 横滚」赔掉。
3. **年月标签是 sticky 的**，一直吸在可视时间轴的左沿 —— 一期这是核心分组格里的 sticky
   内层白给的，二期自己实现，细节见下面「年月标题为什么吸左」。

### 三个层，两套遮挡规则

插件往 `.vt-client` 里塞三个绝对定位层，从下到上：

| 层 | 装什么 | 怎么定层序 |
| --- | --- | --- |
| `.vtp-gantt-bg` | 周末底纹、桶/分组网格线 | **没有 z-index**，且是 `.vt-client` 的**第一个**子节点 |
| `.vtp-gantt-layer` | 甘特条、汇总条、里程碑竖线、今天线 | `z-index: 3` |
| `.vtp-gantt-flags` | 出头的旗标 / `T` | `z-index: 12`（要盖过表头的 10） |

覆盖层的 **3** 落在「盖住单元格底色」与「被冻结的任务列盖住（4）」之间 —— 横滚时条会正确地
滑到左侧任务列**之下**，而不是浮在上面。

底纹和网格线单独拆出来、并且**刻意不写 z-index**，是为了让**分组行整行把它们挡住**：
分组行是结构分隔行，周末的灰底从它身上透出来看着像渲染残留（实测反馈过）。
不写 z-index 的元素按 **DOM 顺序**绘制，所以它排在 `.vt-table` 前面就等于排在所有单元格
底色之下 —— 分组行那个不透明的 `.vt-group-cell` 自然盖住它，而数据行的 `td` 是透明的，
底纹照样透出来。给它任何 z-index 都会跳到分组格上面，遮挡就失效了（`gantt.css.test.ts`
把这条钉住了）。

同一层里为什么不能靠 z-index 分：分组格若写了 z-index 就会变成层叠上下文的一员，
把 `.vt-group-content`（z-index 4，横滚时用来盖住滑过来的汇总条）也一起压下去。
核心那边因此只给 `.vt-tr--group > .vt-group-cell` 写 `position: relative`、**不给** z-index。

### 条内文字的颜色

**只用黑或白**，取所压那块底色的反色（`inkOn()`，阈值 0.179 = WCAG 相对亮度那套的标准
分界，两边对比度都不低于 4.5:1）。

麻烦在于条内有**两块**底色：左边一段是进度实色，右边是浅底。一个文字只能一个颜色，
所以按**标签中点落在哪一块**定 —— 单一临界点，说得清也测得住。

- 中点在进度段上 → `inkOn(实色)`；
- 中点在浅底上 → 主题正文色。浅底是「主色 14% 兑在行底色上」，而行底色由主题给
  （浅色主题白、深色主题深），所以直接用主题那支正文色比在这里把复合色算出来再猜反色更可靠；
- 实色条（`tint >= 1`）两块底色本来就一样，与落点无关；
- 标签移到条外时用的是另一个变量（`--vtp-gantt-bar-text-outside`），不参与这套。

早先条内文字用的是**主色本身**（照抄选项胶囊的「浅底 + 主色字」）。那在浅底那一段没问题，
可文字是压在进度实色段**上面**的，而实色段就是主色 —— 同色叠同色，进度一超过文字宽度
那半截字就凭空消失了（真实数据里大多数任务进度 80%+，等于常态失踪）。

### 右上角的粒度切换器

日 / 周 / 月 / 季 + 「今天」，悬浮在**时间轴的右上角**（年月那一行的右端）。

为什么做进插件而不是留给使用方摆按钮：它要摆对位置得知道**时间轴段从哪一列开始**、
**表头第一行多高**、**纵向滚动条占多宽** —— 这三个量只有插件手里有，留给接入方就是让每个人
把同一套几何重算一遍。位置与选中态只在几何变化时同步一次（和收起按钮同一条路），
不在每帧的热路径上。

- 挂在 `ctx.rootEl` 上、绝对定位、`z-index: 12` —— **三件悬浮件里最低的一件**，见下面
  「悬浮件的层序」。表头是核心拥有的 DOM，插件只可追加、不可重排
- 落点与**年月标题吸左**是配套的：那一行的右侧本来就空着
- 当前档位是实心主色 + `aria-pressed`；「今天」是个动作不是档位，所以用描边而不是填充
  （否则看着像第五档）
- `onZoomChange` 只在**用户点它**时触发；`setGanttZoom()` 走 API 不触发 —— 那是使用方
  自己调的，它已经知道了（与 `onChange` 只在拖拽时触发是同一条约定）
- 自己做的话 `zoomSwitcher: false` 关掉，再把 `setGanttZoom()` / `scrollGanttTo()` 接到
  你自己的按钮上

### 年月标题为什么吸左

**这不是观感问题，是信息不丢。** 一个月在日视图里跨好几屏，滚到后半段时屏幕上只剩一排
日号 —— 「现在看的是哪年哪月」全靠这个标签一直挂在可视区左沿。居中反而更糟：一个跨两屏的
「2026年8月」会飘在屏幕正中间，与哪一列都对不上。

实现是分组格里的一个 `position: sticky` 内层（一期这是核心分组格白给的，二期表头由插件
自己画，所以自己实现）：

```css
.vtp-gantt-head__group {          /* 一格 = 相邻同年月的那一串桶 */
  overflow: hidden;
  overflow: clip;                 /* ← 关键，见下 */
}
.vtp-gantt-head__group-label {
  position: sticky;
  left: var(--vtp-gantt-head-inset, 0px);
}
```

两个坑都踩过：

1. **裁剪必须用 `overflow: clip`，不能用 `hidden`。** `hidden` 会让分组格自己成为一个
   **滚动容器**（scrollport，只是滚动条不可见）—— 而 `position: sticky` 是相对**最近的
   滚动容器**吸附的，于是标签变成「相对这一格吸附」，而这一格永远不滚：吸附完全失效，
   标签跟着格子一起滚出屏幕，年份就此看不见。`clip` 只裁剪、不建滚动容器。
   两条一起写，旧浏览器留 `hidden` 兜底裁剪（只是没有吸附）。
2. **吸附位置要让开左上角那颗「收起任务列」按钮。** 它绝对定位在 pane 的左沿、`z-index: 13`
   压过时间轴表头，标签吸到 `left: 0` 正好整块躲到它背后 —— 而这个标签存在的理由恰恰是「还能
   看见年月」。竖带宽度由 JS 发布成 `--vtp-gantt-head-inset`（`panelToggle: false` 时不
   发布，缺省 0）。

### 悬浮件的层序：切换器 < 收起按钮 < 左表表头

粒度切换器、收起按钮、调宽把手三件都绝对定位在 `.vtp-gantt-split` 上、都只浮在表头那一条里。
平时它们互不相干，**时间轴被挤到 120px 下限时就开始互相压** —— 实测那一刻的横坐标：
左表 `.vt-header` 占 29~1131、收起按钮 1132~1148、切换器 1082~1248，后者同时压住前两个。
所以这几层的次序是有理由的，不是排版顺序：

| z | 谁 | 为什么在这一层 |
| --- | --- | --- |
| 10 | `.vtp-gantt-pane__head` 时间轴表头 | 悬浮件都要浮在它上面 |
| 12 | `.vtp-gantt-zoombar` 粒度切换器 | 最低：它最宽，挤窄时该被别人裁掉 |
| 13 | `.vtp-gantt-panel-toggle` 收起按钮 | 唯一的恢复路径，不许被切换器埋掉 |
| 14 | 左表的 `.vt-header`（插件抬上来的，核心给的是 10） | 甘特的悬浮件不许盖到任务表的列标题上 |
| 15 | `.vtp-gantt-resizer` 调宽把手 | 分界线得一直抓得到，包括表头那一段 |
| 16 | `.vtp-gantt-marker-popup` 里程碑浮层 | 浮层开着时谁都别盖它（尤其那条透明的把手） |

两个具体后果，都是实测出来的：切换器压住收起按钮时，那颗按钮是把时间轴救回来的唯一路径，
被埋了甘特就卡死在那个宽度上；切换器伸到任务表的列标题上面时，两样都是「表头里的字」，
一个浮在另一个上面看着就是渲染错乱。正确的观感是**切换器被分界线裁掉**（代价是极窄时
最左边那一两个档位看不见了 —— 那个宽度下时间轴本来也放不下这个切换器）。

抬左表表头用的是 `.vtp-gantt-split > .vt-root > .vt-header`（三个类）：核心那条只有一个类，
特异度更高才不看两份样式表的加载顺序。只抬**表头**不抬表尾 —— 下边缘没有悬浮件。

吸附范围仍然被**自己那一格**夹住（sticky 的天然行为）：滚到下一个月时，这个月的标签跟着
自己格子的右边缘滑走，下一个月的接上来 —— 于是左沿始终有且只有一个年月标签。

### 时间范围：两端各留若干个**桶**，谁动都重判

不给 `range` 时范围从数据推断，两端各留 `rangePadBuckets` 个桶（默认按 zoom）：

| zoom | 桶数 | 折合时长 | 每侧像素（默认桶宽） |
| --- | --- | --- | --- |
| `day` | 14 | 两周 | 476 |
| `week` | 8 | 两个月 | 416 |
| `month` | 6 | 半年 | 384 |
| `quarter` | 6 | 一年半 | 432 |

**单位是桶而不是天**，这一条是被周/月/季视图逼出来的。固定留 14 **天** 时，日视图两端
各多 14 列，换到周视图只剩 2 列、月视图 0～1 列 —— 一切过去甘特区就塌成中间一小条，
右边全是空白表格。边距的作用是「给条留出可拖动的落脚地」，这件事的度量单位天生是**格子**。

代价是**换粒度时范围会变**（粗粒度留的绝对时长更长），条的位置跟着整体平移一下。
早先正是为了避开这个才固定成两周，但两害相权：平移只在切粒度那一下看得见，
而「粗粒度下甘特区只剩一小条」是切过去之后一直在的。

自动扩展的判据是「**边距余量还在不在**」，不是「数据有没有超出范围」：

```
在时间轴最后一格点一下新建 → 新任务确实还在范围内 → 旧判据不扩
→ 得到的条右缘正好贴着内容末端，想再往右拖都没地方
```

实测就是这样（新建 `09-08 → 09-09`，而范围末端恰好是 `09-09`）。改成按余量判之后，
同一次点击会把末端接到 `09-24`，条右缘离末端 510px ≈ 两周（日视图 14 个桶）。

**只长不缩**：任务往回缩时不收窄范围，否则拖一下条整条时间轴就重排、条跟着整体平移。

重判的触发点：

| 时机 | 怎么进来的 |
| --- | --- |
| 换了整个 `list` | 核心的 `onDataChanged` |
| **改一行的值**（拖条落定 / 点空白格新建 / 改单元格） | `refreshGantt()` —— 核心的 `onDataChanged` 只在换整个 list 时发，所以插件把重判挂在这里 |
| 点空白格新建、拖条落定 | 插件在 `onCreate` / `onChange` 之后自己再补一次（使用方忘了调 `refreshGantt()` 也不至于僵在旧范围） |

三处都走同一个 rAF 合并 + 「余量够就短路」，所以多调几次不花钱。

### 「今天」摆在正中

时间轴几何重建之后，把今天那条线滚到**可视时间轴的正中**（`centerToday: false` 关掉）。

触发点只有三个：**首次装列、换 zoom、换 range**。刻意**不含**：

- 每帧 / 每次 `refreshGantt()` —— 那样横向滚动会被一直拽回今天，拖条改期更是每拖一下跳一次；
- **按数据自动扩展范围** —— 拖条往右会一路触发扩展，视口跟着跳没法用。

两个实现细节都是实测撞出来的：

1. 滚动**推迟一帧**。`scrollByX()` 按 `scrollWidth − clientWidth` 钳位，而换粒度那一刻
   浏览器还没算出新的 `scrollWidth` —— 上一档粒度全都装得下（可滚动量 0）时，目标位置会被
   当场钳成 0，视口一动不动（实测：日 → 月 → 日 切回来，今天线偏离正中 631px）；
2. 今天**不在**范围内时什么都不做。钳位后它会贴到某一端，那反而像「今天就在最左边」。

范围整体窄于视口时滚不动，今天会停在能滚到的地方（偏差就是那点滚不动的量）。

### 桶数上限

`maxBuckets` 默认 500，超出时**降级 zoom**（不是截断，截断会让任务默默消失）并 warn 一次。

这不是保守估计而是硬约束：核心的 `colgroup` 是**全量**建 `<col>` 并填三张 table
（body / header / footer），`table-layout: fixed` 也要跨全部列算布局。日视图跨五年
= 1825 列 × 3 = 5475 个 `<col>`，已经不是虚拟滚动能救的量级。

现实用法碰不到这条线：日视图跨一个季度 ≈ 90 列，月视图跨十年 = 120 列。
`setGanttZoom('day') + setGanttRange('2024-01-01', '2029-01-01')` 会自动落到周视图（264 列）。

## 纯逻辑层：`@virt-table-pro/gantt/time`

分桶与时间↔像素换算对表格只有 `import type`，单独开了子路径，可脱离 DOM 使用
（服务端预算工期、只想拿一份时间轴列定义）：

```ts
import { buildBuckets, timeToOffset, offsetToTime, snapTime } from '@virt-table-pro/gantt/time';

const buckets = buildBuckets(Date.parse('2026-08-17'), Date.parse('2026-08-21'), 'day');
timeToOffset(buckets, someTime);   // → 浮点数：整数部分是桶下标，小数部分是桶内进度
```

| 导出 | 说明 |
| --- | --- |
| `buildBuckets(start, end, zoom, opts?)` | 切桶。首桶向下归一到 zoom 的自然边界，桶首尾相接无空隙 |
| `buildTimelineColumns(buckets, { prefix, bucketWidth })` | 桶 → 两层列树 |
| `timeToOffset(buckets, t)` / `offsetToTime(buckets, f)` | 时间 ↔ offset，严格互逆，超范围夹到 `[0, 桶数]` |
| `snapTime(buckets, t, 'round' \| 'floor')` | 对齐到桶边界 |
| `bucketStart(t, zoom)` / `nextBucketStart(t, zoom)` / `prevBucketStart(t, zoom)` | 不依赖桶列表的边界归一 |
| `inferRange(spans, zoom, opts?)` | 从区间集合推断范围，两端各留 `padBuckets` 个桶 |
| `toTimestamp(v)` | 归一化日期输入，无法解析时 `null` |

**为什么中间量是「offset」而不是毫秒**：时间轴做成真列之后，月/季视图里各列的**时长不等**
（1 月 31 天、2 月 28 天）而**像素宽度相等**，所以「时间 → x」不能用单一线性系数，
必须先定位到桶、再在桶内插值。而像素换算就退化成一次乘法，且天然免疫核心的列宽拉伸系数
—— 每桶像素宽由 `getColumnRange()` 的实测宽度除以桶数得出。
