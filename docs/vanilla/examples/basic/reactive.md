# 响应式更新

**先说结论：纯 DOM 用法下没有任何响应式——数据改完必须自己说一声。**
说一声只有两个出口：`setList(list)`（数据换了）与 `forceUpdate()`（只重画）。

两者**在表格这一侧**代价相同（都清空行池、重建可视区那几十行的 DOM，与总行数无关），
但**在你的数据这一侧差一个数量级**：`forceUpdate()` 一个对象都不新建，而「为了通知去克隆
整份数组」在 10 万行上每轮要造 10 万个临时对象。所以巨量数据、高频刷新的默认选择是
**原地改 + `forceUpdate()`**，克隆整份留给数据量小或本来就走不可变数据流的场景。

`setList()` 也**不要求**你换新数组——它是命令式调用，传同一个引用照样生效。「换引用」这件事
只对框架端有意义（那是 watch / effect 唯一认得的信号），见
[Vue](/vue/examples/basic/reactive) / [React](/react/examples/basic/reactive) 两页。

## 两个出口，怎么选

判据只有一个：**行集合变了没有**。

```js
const table = new VirtTable(container, {
  list,
  columns,
  itemKey: 'id',
  estimatedSize: 40,
});

// ① 只改字段（行没增没删、顺序不变）—— 原地改，forceUpdate 收尾。不新建任何对象
list[3].price = 99;
table.forceUpdate();

// ② 增删、改序、或改了参与排序/筛选的字段 —— 必须 setList，让表格重跑管线
list.push(newRow);
table.setList(list);          // 同一个引用也生效，不必 list = [...list]
```

`forceUpdate()` 并不是「只重画不算账」：它内部会重算总高度与可视区间，所以**扁平表下原地
增删再 `forceUpdate()` 也是对的**。它顶不住的是**派生列表**：一旦开了排序 / 筛选 / 分组 /
树形 / 客户端分页，表格渲染的是管线算出来的那份派生数组，原地 push 进原数组的新行不在里面；
同理，改了参与排序的字段，`forceUpdate()` 只会更新那一格的内容、不会重排。这两种情况必须
`setList()`（这几条都有 DOM 契约测试钉着，见 `packages/vanilla/src/reactive-update.dom.test.ts`）。

另有两件事只长在 `setList()` 那条路上：**头部插入时的滚动位置补偿**（新数据插在上面而视口
内容留在原处）与**追加时的贴底跟随**。做聊天式追加、或往顶部插历史数据时走 `setList()`。

::: warning 别指望「改完什么都不做」
表格持有的就是你传进来的那个数组对象，原地改动到的就是它。所以只要随后恰好发生一次滚动，
被改过的那些行的 DOM 被回收又重建，新数据就会冒出来——但没有那次滚动时它不会。
这种时好时坏比彻底不工作更难查，所以改完请明确走上面两条通道之一。
:::

## 巨量数据：别为了通知去克隆

`list.map((r) => ({ ...r, tick }))` 这一下要遍历 n 项、分配 n 个新对象，**哪怕真正变了的只有
一项**。10 万行 × 10 字段，连续刷 50 轮（Node 23 / arm64，`--expose-gc`，基线堆 77 MB）：

| 写法 | 每轮耗时 | 堆峰值 | 每轮新建对象 |
|---|---|---|---|
| 克隆整份 `map((r) => ({ ...r, tick }))` | 6.00ms | **569 MB** | 100000 |
| 只展开命中的那项 `map((r) => (hit ? { ...r } : r))` | 0.53ms | 93 MB | 1 |
| 原地改 + `slice()` 换引用 | 0.19ms | 107 MB | 1 个数组 |
| 原地改，引用不变（`forceUpdate()` 档） | 0.13ms | 92 MB | 0 |

第一行就是「内存暴涨」的来源：每轮 10 万个短命对象，V8 来不及回收，堆一路涨到基线的 7 倍多；
换到帧上就是周期性卡顿。而这笔钱只换到「可视区那几十行能显示新值」——不可见行的克隆全部浪费。

所以：**克隆是为了不可变数据流，不是为了通知表格。** 不需要不可变语义时，原地改 +
`forceUpdate()`；需要留在「换引用」这条路上（框架端自动同步）时，用 `slice()` 而不是 `map` 克隆。

## 已经渲染出来的行不会自己重填

表格对可视区内的行做的是增量 patch：**行池里已有的 key 不会重新渲染单元格**
（这是增量 patch 的核心优化，滚动时只有真正进出视口的行才建 / 拆 DOM）。
所以「同一个 key 的行、字段变了」这件事，如果不通知，行就停在挂载那一刻的内容上。

`setList()` 与 `forceUpdate()` 都是通过**清空行池**来解决这件事的——可视区内的行
全部拆掉重建，内容自然是最新的。代价也在这里：一次刷新的开销与可视区行数、列数成正比，
与总行数无关。

## 示例在演示什么

示例每隔一段时间把所有行的价格、涨跌幅、轮次推进一轮，四档更新方式的**视觉结果完全一样**
（除了最后一档），区别写在状态栏的「本轮新建对象」上——把行数调大再对比：

- **克隆整份 + `setList()`**：`list.map(row => ({ ...row }))`，每轮新建「行数」个对象。
  上表第一行就是它。
- **原地改 + `slice()` + `setList()`**：元素复用，每轮只新建一个数组。
  vanilla 其实不需要换引用，这一档是给框架端看的便宜写法。
- **原地改 + `forceUpdate()`**（默认档）：新建 0 个对象，巨量数据高频刷新的首选。
- **原地改（不通知）**：表格完全不知道数据动过，轮次停住。点「手动 forceUpdate()」就会一次
  追上（也可以试着滚动一下，被回收重建的那些行会提前露出新值，就是上面那条 warning 说的情形）。

## 高频刷新怎么写

既然一次通知就重建一遍可视区，**通知次数才是成本，改了多少条不是**。所以：

- 一批变更攒在一起，末尾只通知一次；别每收到一条推送就通知一次
- WebSocket / 定时器这类高频源，用 `requestAnimationFrame` 或节流把一帧内的变更合并
- 交互中的那一格不必整表刷：部分内置单元格组件（`@virt-table/vanilla/components`，
  如 `VtSwitch`）被操作后自己改自己那一格的 DOM，不走 `forceUpdate()`

```js
let dirty = false;
function onPush(rows) {
  applyToList(rows);          // 先只原地改数据，不通知、不克隆
  if (dirty) return;
  dirty = true;
  requestAnimationFrame(() => {
    dirty = false;
    table.forceUpdate();      // 一帧最多通知一次；有增删就换成 table.setList(list)
  });
}
```

## 两种更新手段的分工

| 手段 | 什么时候用 | 顶不住的情况 | 数据侧代价 |
|---|---|---|---|
| `forceUpdate()` | 只改了字段（行没增没删、顺序不变） | 开了管线后的增删；改了参与排序/筛选的字段；头部插入的位置补偿、追加的贴底跟随 | **0 分配** |
| `setList(list)` | 增删、改序、改了参与排序/筛选的字段，或需要贴底/位置补偿 | —— | 传同一引用是 0；克隆整份则按行数收 |

两者在表格侧的重绘代价相同：清空行池、重建可视区行 DOM，与总行数无关。

框架包（vue / react）里 `setList` 由框架代劳：内部一个 watch / effect 比较 `options.list`
的引用，变了就替你调。vanilla 没有那一层，两个方法都自己调——也因此不必为了「让框架发现」
而克隆数据。
