# 项目管理 WBS

一份 **5 期 / 3000 个任务 + 35 个工作包**的工程 WBS：左边是任务表（阶段 → 模块 → 任务，三层树），右边是甘特时间轴，中间那条分界可以拖着调宽度、任务面板也能整块收起。

- **行在两边始终对齐**，纵向滚动、树形展开、排序筛选之后都对齐；
- 时间轴按**时间桶**虚拟化，时间跨度再长、任务再多，DOM 里也只有一屏（看页面上那条统计）；
- 甘特插件只负责时间轴与条形层，其余（行虚拟化、树形 WBS、单元格组件、编辑、行拖拽、筛选、搜索、导出）都是核心能力。

## 可以试的几件事

| 动作 | 看什么 |
| --- | --- |
| **拖条**平移、**拖条两端**改工期、**拖进度手柄** | 松手后左边「开始」**立刻跟着变**（「结束 / 进度」在默认面板宽度之外，把面板横滚一下、或把中间那条分界往右拖就能同时看到）—— 两个方向都通 |
| 双击「开始 / 结束」单元格改日期、改「状态」 | 反过来：条跟着移动、条的颜色跟着换。它们本来就是同一行对象的同一个字段 |
| 点顶部 **甘特图配置 → 开始日期 / 结束日期**，换成「实际开始 / 实际结束」 | 条整体右移一天（实际比计划晚一天开工），**没开工的行整条消失**（它们的实际日期是空的） |
| 配置里 **颜色显示** 从「状态」换成「优先级」 | 同一张图按另一个维度上色 —— 完全不同的两张图，这就是这一项存在的理由 |
| 配置里 **进度显示** 换成「工时(人日)」 | 进度段按 1~12 被当成百分数。那不是 bug，是「选错列」的真实后果 |
| 点 **按工作日算工期** | 装上 2026 年放假安排并跳到最近那个假期（默认就是日视图，斜线只在日粒度画）：斜线那几天不计入条内右端的「n 天」，**9/20 与 10/10 是补班日、照常计入**。假期表与补班判定都是案例传给插件的 |
| 展开到任务，找 **名字带「（待排期）」** 的行，在时间轴上点一下 | 没排期的行没有条 —— 点一下就把日期点出来（`editable.create` → 写回行数据） |
| 右上角切 **日 / 周 / 月 / 季** | 整条时间轴与两级表头重建，条与里程碑竖线自动重算（月视图里各列时长不等，仍然对得上） |
| 点 **只看阶段 / 展开到任务** | 3035 行全展开时，看统计条里「DOM 里常驻多少行」——那个数字几乎不变 |
| 在**表头日期**上 hover 再点 | 加一个里程碑（贯穿所有行的竖线，hover 竖线才显名） |
| 按住任务名左边的**拖拽手柄**上下拖 | 树形下也能换序（核心 `moveRowTo()`，落点能落到某个父节点下） |
| **横滚左边那半张表** | 面板默认宽到「开始」那一列（窄屏更窄），后面的优先级、实际起止、工时靠面板自己横滚 —— 两个 pane 各有独立的横向滚动视口 |
| 把浏览器窗口**拉窄再放宽** | 面板跟着收、时间轴始终留得住；放宽后面板还回原来的宽度 |
| 点 **收起任务表** | 任务列整块收走、时间轴铺满；再点回来 |
| **拖中间那条分界** | 任务面板变宽变窄；拖窄之后面板自己横滚（业务列不会挤成一团） |

## 五个设计决定

**1. 层级用树形，不用 `groupConfig`。** 分组行是核心合成出来的一整格（标题 + 计数），画不出「这个阶段自己的计划工期」，只能有一条汇总条。而 WBS 里的父级本身就是**工作包**：有计划起止、有负责人、有进度，甘特里它就该画自己的条、也该能拖。所以用 `children` 嵌套，父行是普通数据行，每一列照常渲染 —— 插件的 `summaryBars` 默认就是这个语义（`'group'`：囊括线只留给分组行），所以这个案例根本不用配它。案例里模块的计划窗口刻意比后代宽一天 —— 计划工期 ≠ 子任务实际占用。

**2. 条的颜色直接取状态胶囊的配色。** `barColor: { field: 'status', colors }` 把「状态」列的候选项配色搬到条上：条底色 = 胶囊底色（主色浅调），进度段 = 胶囊文字色。于是左边那一列与右边的条是**同一套颜色的两个面**，不用另立一套图例。

**3. 写回在使用方，不在插件里。** 插件不知道你的日期字段叫什么、该存 ISO 串还是时间戳，所以它只回调 `onChange`（带新旧值），写回是案例里那几行：改行对象 → `refreshGantt()`（它自带 `forceUpdate()`，左边的单元格跟着刷）。反过来那半个方向也是使用方接的 —— 每一列都挂了 `onChange: refresh`，因为核心目前没有「某格被改了」的通知。这也是它能同时服务「日期存字符串」与「存时间戳」两种系统的原因。

**4. 假期表是入参，不是插件内置的。** 调休安排每年由政府单独发布、各国各地区都不同，插件内置一份就是内置一份会过期的错数据。所以案例自己带 2026 年那两段（中秋 / 国庆，依据国办发明电〔2025〕7 号）与两个补班日，通过 `holidays` / `isNonWorking` 交给插件 —— 少了补班那一半，9/20 与 10/10 会被当成周末扣掉，那正是国内项目排期最容易算错的地方。项目窗口延到 2027 年的那两个月只按周末算：2027 年的安排还没发布，照 2026 年推一版不如不推。

**5. 面板宽度按容器算，不写死一个数。** 案例先前写死 872px（前七列的总宽），宽屏上正好 —— 而 900px 的视口下它把整条容器占满，时间轴宽 0。糟的不是「看不见」：**分界与「收起任务表」按钮都长在时间轴那一侧**，0 宽之后两个都在容器之外，拖不到也点不着，甘特再也回不来。所以案例按容器挑一个落在列边界上的档位（宽屏到「开始」列、窄屏一路退到只剩任务名），插件那边也补了一道硬约束：面板宽 ≤ 容器宽 − 120px，窗口缩小时自动收、宽回来再还原。

## 为什么有「计划 / 实际」两对日期

不是为了多两列数据好看：配置面板里「开始日期 / 结束日期 / 进度读哪一列 / 按哪一列上色」都是下拉，候选是从**列定义 + 数据**推断出来的（核心的列对象不带候选项定义）。只有一对日期、一个数值列、一个单选列的话，那几个下拉里各只有一个选项，等于这个功能没法试。所以这张表刻意有两对日期（计划 / 实际）、两个数值列（进度 / 工时）、两个单选列（状态 / 优先级）—— 而「计划 vs 实际」也正是项目管理里最常见的那一对。
